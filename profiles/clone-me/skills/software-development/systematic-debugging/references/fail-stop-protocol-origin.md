# Fail-Stop Protocol — Origin & Rationale

## Origin Session

2026-05-16, user批评卡住不汇报的问题。

## 用户原话

> "你真的会是不是自己卡住而没有任何下一步汇报或者进展甚至我都无法打断你"

## 问题本质

工具调用逐次决策模式下，每个步骤看起来都合理（"再试一次"、"换种方式"），
但缺少全局视角判断自己是否在空转。没有内置的"故障计数器"，
所以第3、4、5次试错和第1次看起来一样合理。

正常流程是"调用→得到结果→继续"，失败时也遵循同一模式，
没有在失败后主动输出状态报告的机制。

## 协议设计原则

1. **第一次失败就汇报** — 不等累积到"连续2次"，因为第1次失败后下一个
   工具调用可能覆盖了反馈信息，失去"连续感"

2. **状态可视化** — todo 列表作为任何时刻可读的状态快照，用户一眼看见卡点

3. **测试/验证=只读** — 防止"我让你测试，你在改什么"的越权模式

4. **静默重试=0** — 无论是第1次还是第N次，没有状态报告就不允许下一个工具调用
